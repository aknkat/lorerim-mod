# v0.1.4 diagnostic1：ロード後の不発の診断

主能力800を直接Castしても光らず、同じ状態で内部探知803をCastすると光ったとの実機報告を受けた。探知表示は動くが、主能力の条件・起動スクリプト・制御からの実行を区別する必要がある。

このZIPは診断用の追加MODで、修正済みの本体ではない。v0.1.4の専用スクリプトに `LKS_Probe` 関数だけを追加する。保存変数・プロパティ・レコードを増やさず、既存の全関数のコンパイル済み命令と保存レイアウトが変わらないことを検査する。

## 導入と実行

1. ゲームを終了し、このZIPをMO2に**別MODとして**導入する。本体v0.1.4も有効にしたまま、左ペインで診断MODを本体より下へ置く。本体の専用PEX・PSCだけを意図して上書きする。
2. 完全終了・再起動後、問題の検証用セーブをロードする。付け外しや通常の発動確認を挟まず、通常画面で65秒待つ。
3. IndexがFE:CFDのままなら、コンソールで `cqf FECFD804 LKS_Probe` を1回実行し、コンソールを閉じる。Indexが変わったら現在のものに合わせる。
4. `LKS DIAG1` の画面の内容を記録する。閉じた後にNPCが光ったかも分かる範囲で記録する。実行エラーや画面が出ない場合は、その結果自体を記録し、繰り返しコマンドを入れない。

## 表示と影響

画面はQuestのRunning状態、種族条件、探知SPELの参照有無、Native時計、保存した期限、実行前の残り秒数、TryActivateの戻り値、実行後の残り秒数を示す。

**Probeは現在と同じ制御を1回呼び、受理された場合は探知と通常のクールダウンを開始する。** 読み取りだけの関数ではない。Accepted=Trueは制御関数がTrueを返した意味で、描画の成功を証明しない。通常の主能力から呼ばず直接コントローラーを試すことで、その手前の条件や入力効果と区別する。時計の単位・進行と保存復元の実機確認も引き続き必要。

診断専用の保存変数、タイマー、OnPlayerLoadGame、Alias、装備変更はない。スクリプト情報を含む本体の保存状態への依存は残る。**この版でのCQF呼び出し・画面表示は実機未検証。** セーブせずに終了し、診断が終わったらゲーム終了後に診断MODだけを無効化すると元の本体PEXへ戻る。本体を削除・Resetする必要はない。

## 制作・検査

`tools/build_diagnostic.py` が公開済みv0.1.4 ZIPのSHA256を固定し、そのPSCへ診断関数を追加してstrictコンパイルする。元の関数・保存変数・プロパティの一致を解析し、実際の診断PEXで準備完了・待機中・別種族・未設定SPELの4ケースを模擬実行する。Debug.MessageBoxの宣言だけをコンパイル用に使い、ゲームのDebug.pexは同梱しない。

通常ビルドと同じツール・Wine環境で、`python3 tools/build_diagnostic.py --dotnet /workspace/scratch/dotnet/dotnet --caprica /workspace/scratch/caprica-bin/Caprica.exe --wine /workspace/scratch/wine-root/usr/lib/wine/wine64`。ソースZIPには本体PSCと関数生成コード、検査用ホストを含む。実機の時計や画面動作を模擬実行の合格で保証するものではない。
