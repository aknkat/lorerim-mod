# v0.1.4：解除イベントに依存しないクールダウン

## 実機報告と判断の範囲

ユーザーはゲームを完全終了してからロードしている。v0.1.3のクールダウン外で保存した場合は即発動できる。一方、待機中の保存では1分以上待っても発動せず、パワーの付け外し後に、直後でも正確な60秒後でもない途中のタイミングで使えると報告された。

付け外し自体がフラグを解除する処理はない。更新イベントの消失・遅延、装備入力、別のゲーム側状態のどれが原因だったかを実機ログで確定したわけではない。ただし、解除イベントが届かなければ保存フラグが永久に残る設計上の弱点は確認できるため、そこへの依存をなくす。

## 現在の方式

同じ専用QUSTのFloat変数 `readyAtHours` を使い、入力時だけ `Game.GetRealHoursPassed()` と比較する。これはバニラAPIで、追加のSKSE依存ではない。期限は受理した時刻から1/60時間先。拒否した再入力では書き換えない。時刻取得などのNative呼び出しをすべて終えた後、共有期限を読み、次の外部呼び出しであるCastより前に確定する。

- 新しい更新イベント登録・Wait・常駐ポーリングはない。
- 解除イベントが失われても、入力時に期限を判定できる。
- 新規レコード・Alias・ロードイベント・装備変更を追加しない。v0.1.3の5レコードのフィールドと入力PEXをバイト単位で維持する。ESPヘッダーの版説明とマニフェストは更新する。
- 保存する期限という状態は残る。標準プレイ時計の保存・進行に依存するため、セーブへのリスクがなくなったとは扱わない。
- 標準時計が大きく巻き戻り、残り時間が63秒を超えた場合だけ、その入力を拒否し、期限を現在から60秒先へ一度補正する。通常の再入力やロードで期限を更新する処理はない。この補正では以前の正確な残り秒数を再現できない。

Float時計の丸めにより60秒境界に誤差が出る。ゲームを止めている時間、メニュー・睡眠・ロード中の進み方、長時間プレイ時の精度は実機確認事項。検査ホストでの時計の保存・復元を、ゲームエンジンの実証とは扱わない。

## v0.1.3からの移行

旧 `coolingDown` 変数は互換性のため残すが、発動を拒否する判定には使わず、入力時に片付ける。新しい期限のない旧セーブでは最初の有効な入力を受理する。**版を更新した直後の旧クールダウンは一度リセットされる。** 旧フラグから残時間を推測して復元しない。

旧版で登録したOnUpdateが遅れて届く場合のイベント関数も保持する。ただし、旧変数をFalseへ戻すだけで、新期限には触れない。旧イベントで新しいクールダウンが解除されることはない。既存のパワーの削除・再追加やクエストのResetは行わない。

## 検査と未確認事項

コンパイル済みPEXで、通常の0/30/65秒、200回の再入力、Native呼び出し途中の再入、更新登録をすべて失うロード、旧フラグだけを持つ保存、遅延した旧イベント、時計の巻き戻りと長時間プレイのFloat精度を検査する。時計は模擬Native APIで、演算は32bit Floatへ丸める。

**v0.1.4の実機修正結果は未確認。** ゲームを終了・再起動するLoreRimのロード手順に従い、待機中に別名保存したセーブから、付け外しなしで残り時間後に発動できるかを確認する。旧版で失敗した同じセーブを更新直後に試すだけでは、移行時の一度だけのリセットを確認したにすぎない。v0.1.4で発動・保存した状態を別途確認する必要がある。
