# 検証記録：v0.1.4

対象：Skyrim SE 1.6.1170 / LoreRim v5.0.4.8 Default / Requiem / Cabbage ENB。制作機でゲームは起動できない。**v0.1.4はファイルと模擬実行の検査に合格したが、実機ではロード後の不発が続くとの報告。未解決。**

## 実機報告

- v0.1.0とprobe1は探知が表示されなかった。標準VoiceAuraWhisper1は同環境で赤く広範囲に表示された。
- ユーザーの読み取り専用xEdit出力（3494 loaded files）で、Area/No Area/FX Persist/Actor Value、シェーダーとキーワードの最終定義、VMADを照合した。IndexはFE:CFD。詳細は [レコード比較](RECORD_COMPARISON_0.1.1.md)。
- v0.1.1で近くのNPCの赤い表示を確認。待機後は再使用できたが、途中の再入力後に初回から65秒経っても発動しなかった。
- v0.1.2は押すたびに発動し、NoRecast単独の制限方式は不成立だった。
- v0.1.3は60秒ごとの再発動を確認。ただし完全終了後でも、クールダウン中のセーブをロードすると1分以上待っても発動しない。待機中でなければロード後に即発動する。パワーを付け外しした後、直後でも正確な60秒後でもない途中のタイミングで発動すると報告された。
- 付け外し自体がスクリプトの待機を解除する実装はない。イベントの欠落・遅延や装備経路など、実機内部の根本原因はログで確定していない。セーブ破損を確認した報告でもない。
- Y＋RTでパワー発動。Y長押しで「no items to interact with」、Y＋RT連打で採取・飲食のような音。発生元は未特定。再使用待ち・残り時間は有効な効果に表示されない。他MODやキー設定の競合と断定しない。
- v0.1.4でもロード後に発動せず、付け外し後にクールダウン時間を経て発動するような挙動と報告された。正確な経過秒数や内部値は取得していない。期限方式への変更で解決したとは扱わない。
- その後、ロード後65秒待ち、通常の発動確認や付け外しを挟まずに主能力800を直接Castしても光らなかった。同じ状態で通常画面3秒を挟み、内部探知803を直接Castすると光った。探知と表示経路がロード後に動くことを確認した。主能力の適用条件・起動スクリプト・制御からの呼び出しは引き続き未確定。
- diagnostic3の実機スクリーンショットで数値報告まで到達したことを確認した。Quest running / Race allowed / Spell bound / TryActivate acceptedはいずれもTRUE。時計11.348222、保存期限11.316698、実行前残り-113.485336秒、実行後残り43.025208秒。この試行は保存期限で拒否されず、元のTryActivateのCast呼び出し後のTrue返却まで到達した。参照ありは正しいFormIDの照合や描画成功の証明ではない。付け外しを含む実行手順の遵守と、今回NPCが光ったかは画像だけでは確認できない。
- その後ユーザーは「ちゃんと見てなかったが光らなかったような気がする」と回答。今回の発光は未確認として扱い、描画成功・失敗のどちらにも確定しない。
- diagnostic4で「何も起きない」と報告された。通知については「文字は見逃した」と補足されたため、通知なしとは確定しない。実機ログは取得していない。
- 診断5を渡した後の「何も起きない／以前と同じno nearby target to interact with」という報告は、その直後に診断MODを有効化していなかったと訂正された。この試行を診断5の結果には数えない。
- 診断MODを有効化した再試行では、画像右上に `LKS: INPUT` と `LKS: ACCEPTED - cast requested` が確認でき、ユーザーは「光らない」と報告した。同じ画像には `No nearby items to interact with` も写っている。今回の入力イベントと元のTryActivateの受理・Cast後のTrue返却までは実機で確認できた。入力がMODに届かなかった、または待機中として拒否された試行ではない。通知だけではCast先の実際のFormID・効果の適用・表示の発生時刻までは証明できない。
- 続けて内部探知803を直接Castすると「光った」と報告された。Indexの「f5」という略記はMO2の表示全体では **FE:CF5** とユーザーが確認した。途中のFE:0F5というこちらの解釈は誤りだった。現在の内部探知はFECF5803、専用QuestはFECF5804。古いxEdit出力のFE:CFDを現在のコマンドへ固定しない。
- SQVのDetectionSpellは **FECF5803** とユーザーが確認した。保存された参照も正しい。入力イベント・待機判定・保存参照・直接Castの描画までは確認できたが、PapyrusからのCastが発光しない原因は未確定。

## 現在の切り分け

主能力800の直接Castは不発、制御を迂回する803の直接Castは表示できた。装備だけを原因とせず、主能力の条件・スクリプト・制御を調べる。

`diagnostic1` は専用コントローラーへLKS_Probe関数だけを追加する。元の全関数と保存変数・プロパティの不変性、準備完了・待機中・別種族・未設定SPELの4ケースの診断画面を、実際のPEXと模擬APIで検査する。Probeは現在のTryActivateを直接1回呼ぶので、受理された場合は通常の期限更新と探知を実行する。診断のための新しい保存変数・タイマー・装備変更はない。既存25検査も、拡張した検査ホストで再確認する。CQFからの実行・画面表示は実機未確認。手順は [診断文書](RELOAD_DIAGNOSTIC.md)。

アンダースコアが入力できないとの報告を受け、`diagnostic2` は英字だけの `LKSProbe` 別名を追加する。診断1の全関数・保存レイアウトの不変性と、小文字の呼び出しからの4ケースを検査する。画面内容・発動処理は同じ。新しい別名は診断MODの更新と再起動後に使う。

その後 `cqf not found` と実機報告があり、diagnostic1/2のCQF手順を撤回した。Skyrim上での利用確認がないまま案内した誤り。`diagnostic3` は通常の能力のOnEffectStartへ最初の表示・中断箇所の表示・コントローラーの診断呼び出しを追加し、コンソールを使わない。元のコントローラー処理と両スクリプトの保存レイアウトは維持する。戻り値のないDebug.MessageBoxのコンパイル用宣言を修正する。元の4ケースに加え、入力からの7ケースを実際のPEXと模擬APIで検査する。画面表示とゲーム内での保存済み実行状態は未検証。診断はセーブせず終了する。

diagnostic3の数値画面の表示はその後実機で確認できた。今回の期限は満了し、制御関数は受理しているため、この試行を「クールダウンが残って拒否された」とは説明できない。診断追加前に起きた不発の原因が解決した証拠でもない。探知Castは数値画面を出す前に呼ばれ、表示は2秒しかないため、画面を閉じた後に光らなくても今回のCast失敗とは断定できない。実行後43秒という値からタイマーのリセットや処理遅延の原因を断定しない。画面追加により実行のタイミングも変わるため、原因未確認のまま次の修正版は作らない。

diagnostic4は診断用ダイアログをDebug.Notificationへ置き換え、数値はDebug.Traceへ出す。これにより発光の前後にメニューを開かず、1回の入力で通知と発光を確認できる構成にする。元の発動条件・保存レイアウト・TryActivateは変えない。新しい状態・タイマー・Waitは追加しない。画面への通知が実機でどう表示されるかと、今回の探知描画は未確認。通常版の修正版とは扱わない。

**diagnostic4の使用は撤回した。** 公開されているSkyrimのDebug.pscではNotificationの引数は文字列1つだけだが、診断4は存在しないBool引数を付けた宣言でコンパイルしていた。最初の通知呼び出しで実行が失敗し得る。検査用ホストも誤った2引数を許可しており、この不具合を検出できなかった。構造検査・逆コンパイル・模擬実行の合格ではNative APIとの適合まで保証できない、こちらの検査不備だった。実機での中断原因はログがないため未確定。

diagnostic5は通知を1引数へ修正する。BellCubeDev/papyrus-indexの固定コミット `ec822650d44885707c01e90eeb569551f0ab8ddb` のSkyrimSE/vanillaにより、使用するAPIを含む10宣言の戻り値・引数型・Global有無を照合した。引用元URL・行番号・ファイルSHA256を `tests/fixtures/skyrim-vanilla-api.json` に保存する。`tools/verify_papyrus_api.py` がコンパイル用宣言と、実際のPEXの引数数・型・戻り先を独立に照合する。公開済み診断4の実ファイルがこの検査で不合格になる回帰テストを追加する。元のTryActivate・保存レイアウト・ESPは変えない。通常版のロード後不発の解決や実機の描画成功を、この訂正だけで宣言しない。

診断5の有効化後、INPUTとACCEPTEDは出るが発光しないとの結果を受けた。次は診断MODを増やさず、そのままの状態で既知の内部SPEL803を直接Castして同じNPC・表示と比較する。Indexが以前と同じFE:CFDなら `player.cast FECFD803 00000014 left`。この時点で光れば、対象・探知レコード・描画が動くことを確認し、保存された参照・スクリプト呼び出し・適用タイミングなどとの差へ調査を絞る。光らなければ、現在の対象・効果の状態・探知条件も引き続き対象にする。Spell.Castの戻り値はNoneであり、ACCEPTEDはエンジンが効果を適用したという戻り値ではない。インタラクションの文言は本MODのスクリプトでは出していないが、発生元や他MODとの因果関係は特定していない。

この比較では直接Castで光ったと報告されたため、探知データやENB設定を変更せず、保存されたDetectionSpellの参照とスクリプトからの適用を調べる。現在のIndexを確認したうえで、読み取り専用の `sqv FECF5804` でQuestの実行状態と表示可能なスクリプト変数を取得する。DetectionSpell（またはその自動変数）が見えればFECF5803を指すか照合する。表示されなければ、その結果自体を記録し、QuestのStop/Start/Resetや他MODの変更で回避しない。参照が誤っているとも、Spell.Cast自体の不具合とも、この段階では断定しない。

SQVで参照が正しいと確認された後、ユーザーから他MODの挙動を十分調べていないとの指摘を受けた。新規レコードのみ・既存レコードの上書き0件という検査は、実行時の干渉を否定しない。コンソール経由で光ることも、Papyrus経由が同じPerk・Nativeフック・詠唱状態の扱いになることを証明しない。INPUTとACCEPTEDが見えても、同時のインタラクション処理や他の詠唱処理による中断・上書きは未検証。これらを本MOD自身の不具合とも他MODの不具合とも断定しない。

試験版の追加やCast方法の変更を行う前に、使用中のMO2プロファイルのmodlist.txt・plugins.txt・loadorder.txtを基に、関係する入力・詠唱・魔法処理のMODと生成パッチを特定する方針にした。この時点では一覧と実行時ログがなく、確認した公式GitHubツリーにも使用中プロファイルの構成ファイルはなかった。既存のxEdit出力はSPEL/MGEF/EFSHが中心で、全Perk・DLLフックの検査を済ませた資料ではない。全MODの無差別な無効化やキー変更は根拠なく行わない。

その後、ユーザーから実際の3一覧を受領して照合した。有効プラグイン3413件はすべてloadorderに含まれ、相対順序も一致し、重複は0件。診断5は本体より高い優先順位で有効、LKSのESPは最後だった。関連する入力・詠唱・Papyrus・魔法処理のMODと生成パッチを抽出し、公開実装を調べた。Papyrus Tweaksの標準値はNative高速化が無効、標準除外にCastが含まれるため、導入されているだけで原因とはしない。次は実効PapyrusTweaks.iniの確認へ限定する。DLL実ロード・設定・全ファイルの勝者は3一覧では分からず、特定の実行時競合も未確定。追加の試験版・ゲーム内テストは作成していない。資料のハッシュ、行番号、固定ソースと限界は [プロファイル照合記録](RUNTIME_INTERACTION_AUDIT.md) にまとめた。

## v0.1.4の変更と検査

解除イベントが届かなければフラグが永久に残る構成をやめ、入力時に標準プレイ時計と保存した期限を比較する。[変更の詳細](RELOAD_FIX_0.1.4.md)。旧版フラグは判定に使わない。新しい更新登録・Wait・Alias・ロード時の装備変更はない。

`python3 -m unittest discover -s tests -v`：**25 tests / OK**。実際にコンパイルしたPEXの命令を検査用ホストで実行する。API、時計とその保存復元は模擬で、ゲーム本体の時計・入力・描画は検証しない。

- ESL・Localized、Skyrim.esmのみへの依存、固有5レコード、既存レコードの上書き0件、解決するローカル参照と文字列。
- Lesser Power、Self、Fire and Forget、コスト0、1秒の入力効果、プレイヤーと通常/吸血鬼Khajiitのガード。自己参照HasMagicEffect条件なし。
- v0.1.3配布ZIPのSHA256を固定し、5レコードの全フィールドと入力PEXが同一であること。v0.1.1由来の探知データとも照合する。
- Area 27、Magnitude 0、Duration 2、FX Persist、Actor Value None、共通シェーダーDC209、Area Effect Ignores LOS。距離560 unitsと死体・アンデッド・機械・NoDetectLifeの条件表。
- 0/30/65秒の判定、200回の新規入力効果で期限が延びないこと。GetRace・時計取得・Cast中の再入でも受理が1回に留まること。
- **更新登録を一切復元しない**模擬ロードでも、発動15秒後に保存した期限が約45秒後に満了すること。準備完了状態でロードしても勝手に発動しないこと。
- 新しい期限のない旧セーブで、残ったTrueフラグが使用を妨げないこと。遅延した旧OnUpdateが新期限を解除しないこと。
- 時計が大きく巻き戻った場合に期限を一度だけ60秒先へ補正し、再入力で延長し続けないこと。
- 演算とAPI戻り値を32bit Floatに丸め、0/100/1000/10000時間で58秒時点の拒否と62秒時点の受理を確認。
- コンパイル済み制御に更新登録・Wait・装備変更の呼び出しがないこと。PEX構造・正しい長さ・破損ファイルの拒否。

ビルド・配布検査では、Caprica v0.3.0のstrictコンパイル、MutagenによるESP/PEXの独立読み込み、Pythonリーダー、Champollionの逆コンパイル、再現ビルド、ZIPのCRC/SHA256・Data配置、FSMPとのパス比較を行う。

旧版の検査ホストはNative更新登録が正しく復元されることを仮定しており、その仮定をゲームで検証できていなかった。v0.1.4では更新登録を失うケースも対象にするが、代わりに標準時計の進行・復元を模擬する仮定がある。25件合格をゲーム内の安全性の証明とは扱わない。

## LoreRimの運用ルール

ユーザー提供の [v4.lorerim.comのSafe Saving本文](https://v4.lorerim.com/home) に従う。公式サイトは制作環境のプロキシで403拒否されるため直接再取得しておらず、v5現行ページとの同一性も未確認。

ロードはゲームを終了・再起動してから行う。戦闘・重いスクリプト演出中・セル移動直後の保存、短い間隔での連続保存を避ける。保存した処理状態の不整合を持ち越すリスクを考慮し、確認には別名の検証用セーブを使う。軽量な処理や上書き0件でも、追加した保存状態のリスクはなくならない。

## 未確認の点

- **v0.1.4で待機中に保存・完全終了・再起動して、付け外しなしで残り時間後に発動すること。** ゲーム本体の標準プレイ時計と期限の復元、再入力・装備状態は未検証。
- 標準時計のメニュー・ポーズ・睡眠・ロード中の進み方、60秒境界の精度と大きなFloat値での丸め。時計補正時には正確な旧残時間を保持できない。
- v0.1.3からの既存セーブ更新と旧実行中スタック。新期限がない旧セーブは初回だけクールダウンをリセットする仕様であり、通常の保存復元の合格とは別。
- 実効半径約8m、2秒の正確な表示時間、除外対象、壁越しや自身の発光、吸血鬼Khajiit。近距離の赤い表示は過去のユーザー報告あり。
- 他MOD・将来の生成パッチやロードオーダーの変更、専用QUST停止・無効化後のセーブからの完全除去。

既存レコードの上書き0件は直接のレコード競合を避ける構成の検査結果であり、セーブやすべてのMODとの相互作用まで保証するものではない。
